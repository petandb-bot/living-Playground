# LIVING PLAYGROUND — 基本設計 v0.1

> **2026-11-17 / α実装状況:** [v0.1.0-alpha.1](../README.md)としてTHUMP / CHIRP / TICK、限定的LINK、16ステップの疎な反復、局所MUTATE／UNDO、Bug 1体、ピクセルPLAYFIELDを試作済み。主要な音響テスト11件と静的ビルドは成功。音楽的な好みの評価、iPhone Safariでの実機演奏、録音機能は未検証・未実装です。最初の段階は依存ライブラリのない**ブラウザES Modules + Web Audio + Canvas 2D**で構成し、規模や性能要件に応じてTypeScript等を導入します。視覚指針は[ART_DIRECTION.md](ART_DIRECTION.md)を優先します。

## 1. コンセプト

「小さな電子音の装置を置き、組み合わせ、触ると、画面内の生き物と音楽が互いに反応する遊び場」。

ユーザーが行うことは **置く・叩く・つなぐ・動かす・覚えさせる**。シンセシスの理解や大量のパラメーターを要求しない。それでも音楽として反復、休符、音程的な関係、展開を作れる。見た目の楽しさが主役の一つだが、結果は演奏・録音可能な楽器であることを必要条件とする。

**避けるもの:** 通常のモジュラーシンセの縮小版、16パッドUIの単純移植、DAWのタイムライン、常に音が発生し続ける自動生成、音に無関係な派手な演出、元ゲームの画面やキャラクターの模倣。

**音色:** 玩具的な丸さと、不均質なFM、プラスチックの打撃、合成音声の断片、電子的な事故、冷たい共鳴。必ずしも可愛い音ではない。音色の粗さは保存し、不要なクリック・過大出力・DC・制御不能なフィードバックは除く。

## 2. 受け継ぐ価値のある実装

### WRONG NUMBER
実際に確認した `audio.js` と `app.js` を参照する。

- **6 kits × 16 voices:** CANDY KIT、TOY MALFUNCTION、SUGAR POISON、ROTTEN CARROT、WORM PARADE、BAD SPELLING。特に ROTTEN CARROT の有機的FM/虫めいた短音、TOY MALFUNCTION の弾性・不格好な音程、BAD SPELLING の合成音節を、新しい数種類の発音体へ選択的に再構成する。
- **STUTTER / REVERSE / TAPE BEND / CRUSH:** 別の発音体に接続したときに起こる音響的な変化の出発点。
- **空隙のある生成:** `generateOpen()` は2小節を10–16ヒット程度に保ち、音を加える余白を作る。過密な同系統のヒットを避ける `balancePattern()` の考え方を継承。
- **MUTATE / UNDO:** 音楽的な錨を残しながら一部を組み替え、変更前へ戻せる。長押し／連打で音が変化する `playPad()` の発想も重要。
- **小さな反応:** `maybeReply()` は人間の演奏の後に一回だけ控えめに応答する。常にAI的に返答するのではない、希少な掛け合いを採用候補とする。
- **描画:** LCDのウサギは拍や事故に反応する。新作ではウサギの形状や振り付けを流用せず、画面と音が結びつく原理を参考にする。

### SIGNAL MACHINES
- 必要な発音体のみを選択して、音響処理・共鳴・ピッチ集合・イベント制御のアルゴリズムを移す。
- 安定した master 出力、録音境界対策、決定的seed、WAV出力、ブラウザーでのテストと保存の思想を再利用する。
- 68モジュール全体、複雑なポート一覧、旧ワークスペースやプリセットを移植しない。新しい音・UI構造に合わせて必要最小限のアダプターを作る。

既存リポジトリの公開状態だけで第三者の権利が消えるわけではない。利用するライブラリ・アセットのライセンスを個別に確認し、オリジナル素材のみを新規制作する。コードの流用箇所は出所を記録する。

## 3. 操作原理

### 3.1 舞台とチップ

- 1画面の **PLAYFIELD**。最初から音を出せる小さな構成を置く。ユーザーのジェスチャーがあるまで音声再生しない。
- 初期同時配置の上限は **4チップ**（後で実測に基づき増やせる）。追加は下部の小さな **+** パレットから。タッチ操作でも操作対象が小さくなりすぎないこと。
- 各チップは **音が出る／意味のある単体動作** を持つ。組み合わせると音色、タイミング、記憶、影響範囲のいずれかが変化する。
- サウンドチップの本体を **タップすると直ちに鳴る**。長押しは音の保持・変化。チップ位置は独立したドラッグハンドルで移動する。設定用の小アイコンから主パラメーター **最大2つ** を開く。
- 一般的なモジュラーの入出力端子は表示しない。**LINK** 小アイコン→相手チップ選択で明示的な関係を作る。リンク解除も簡単に行える。移動だけで配線を勝手に変えない。
- リンクの意味はチップの役割から決め、意図しない種類の信号を自動変換しない。無効な組み合わせは短い説明を返し、音は変えない。
- リンクは細い道のように表示され、Bugはその上を歩ける。音響データは表示に渡さず、イベントや間引いたメーター値だけを描画へ渡す。

### 3.2 最初の6種類（計画）

| 英語名 | 分類 | 単体の楽しさ | 関係を結んだ場合 |
| --- | --- | --- | --- |
| **THUMP** | voice | ゴム・空洞・FMの打撃音 | TICKから拍を受ける／MUTANTで音が変形 |
| **CHIRP** | voice | 虫・玩具のような音程のある音 | TICKからモチーフ／NESTから再生される |
| **MUMBLE** | voice | 合成母音・不完全な音声チップ | MUTANTで短片化／NESTにフレーズを記憶 |
| **TICK** | events | 余白のあるパルス、複数の反復周期 | 声部へイベントを渡し、違う周期を作る |
| **MUTANT** | transform | 選択した短音を壊す／曲げる | 接続音に STUTTER / REVERSE / BEND / CRUSH |
| **NEST** | memory | 直近の演奏イベントを覚え、返す | 声部の発音順序を覚えて再演・変異 |

実際のv0.1第一実装は **THUMP / CHIRP / TICK の3機種 + Bug 1種** に限定する。MUTANT / MUMBLE / NESTは動く核を確認した後に追加する。最初から6種類を一括実装しない。

### 3.3 LINKの型付きルール

- `TICK → voice`: イベント / 発音の契機
- `voice → MUTANT`: 音響処理の入力
- `voice → NEST`: 発音イベントの捕捉（WAV録音とは別）
- `NEST → voice`: 捕捉したイベントを再生
- `voice → voice`: v0.1では未対応（後で相互変調・模倣を検討）

1本のリンクが内部で何をするかを **LINK選択時に一文だけ表示**。複雑なルーティング・マトリックスは作らない。音声ループの無制限な接続を防ぐ。

## 4. 音楽的な骨格

- **共通transport:** 70–160 BPM程度の設定範囲を初期候補とする。タップ音は即時発音し、記録時だけ拍へ寄せる（量子化は選択可能）。
- **TICKのルール:** 8/12/16ステップ相当の周期、休符を標準で含む。規則的な核がありながら、周囲のアクセントや長さはずれる。常に4つ打ちになるわけではない。
- **音程:** CHIRP / MUMBLEに少数の音程的な関係を設定できるが、ピッチ固定を強制しない。5音程度の「親しみやすい集合」と、ずれた集合を選べる設計にする。明確なメロディと不協和の両立。
- **変化:** 各機種が小さな記憶状態を持ち、変異は *一部だけ* 行う。ユーザーの操作で作った核と休符を無断で上書きしない。偶然の発見をすぐにUNDOできる。
- **応答:** 不意の応答は稀で、パターンを静かに破壊しない。密度上限、休止時間、イベントごとの最大発音数を設ける。
- **録音:** 演奏の全体をWAVで録音・出力できることを初期から目標にする。NESTのイベント記憶と、音声ファイルの録音は別システムとして実装する。

## 5. Bugという生き物

Bugは装飾オブジェクトではなく、音楽の状態を読む **small agent**。ただし、初期段階で自律的に音を改変することは禁止する。

### 行動状態の例

`REST → WANDER → INVESTIGATE → RIDE_LINK → KNOCK → REST`

- **音のイベント**で顔を上げたり、チップに近づいたりする。
- **リンク**を移動経路として利用する。リンクの色・明滅は信号の種類ではなく、現在のイベントやエネルギーに応じて変わる。
- **チップの振動**を感じて立ち止まる、リズムに乗る、眠る。全動作が同拍同期にはならず、遅延や個体差がある。
- **直接操作**（Bugを掴んでチップに置く等）だけが、初期版で明示的な音を発生させる。離せば自律移動に戻る。
- 将来的にBugが自律的に楽曲へ介入するなら、PLAY / MISCHIEFのような明示的なopt-in、変化の上限、UNDO/disableを必須にする。

1種類のBugから始め、固有の輪郭と5〜7種類の姿勢変化を与える。既存ゲームのキャラクターやウサギをコピーしない。歩行は滑らかだが、グラフィック構成には小さなセル、強い色面、輪郭を利用できる。

## 6. 視覚とUI

- 80年代アーケードの**色の対比、見通しの良いレイヤー、役割のある小さなアニメーション**を参考にする。粗い巨大ピクセル、CRTノイズ、スキャンラインの常時エフェクトに頼らない。
- 黒〜暗色の舞台に、少数の明快なチップ色と小さなBug。各チップ内のアニメーションは、実際の音響イベントに接続する。
- ケーブルは道、チップは場。読めるラベルと選択状態を優先する。視覚密度を上げても**タッチターゲットは減らさない**。
- 上部は PLAY/STOP とテンポ。下部は + / NEW / UNDO / REC。複雑なパラメーター表示は選択中のみ。
- 機能名とHELPは英語、説明は数語〜1文。完成したパッチでも視覚的に楽しめるが、音を出さなくても「完成」と見えるだけのスクリーンセーバーにはしない。
- 動きは audio time に同期したイベント + 自律行動の両方。描画fpsの揺れが演奏タイミングへ影響しない。

## 7. 技術構成

初期推奨スタック：**Vite + TypeScript + Web Audio API + Canvas 2D**。Canvas 2Dから始める理由は、モジュール内の細かな2D動作と少数のキャラクターだけならWebGLの追加負荷を必要としないため。p5.js 2.xは既存コード移植にメリットがある場面で選択可能だが必須にしない。将来のWebGLは負荷測定後に検討する。

```text
src/
  audio/        # voice recipes, effect adapters, master safety, WAV recording
  music/        # transport, musical events, patterns, seeded mutation, memory
  world/        # bugs, state machines, navigation, link geometry
  chips/        # role definitions, two controls, valid link rules
  ui/           # canvas stage, DOM controls, gestures, contextual help
  state/        # versioned project schema, save/load, undo snapshots
tests/          # transport, voices, links, project versioning, stable output
docs/           # musical studies, technical limitations, measured performance
```

原則：
- **Audio Clock is authoritative.** JavaScript描画タイミングをオーディオスケジューラーに使わない。
- EventBusは `TICK` / `NOTE` / `HIT` / `MUTATE` / `CONNECT` / `LOOP_END` 等の低頻度イベントを扱う。高頻度の音声サンプルをDOMやBugシステムに送らない。
- Web Audioのノード／スケジューラーを最初に利用。連続フィードバックやサンプル単位処理が必要になった時だけAudioWorkletを追加。
- Seed付きランダムで再生の再現性を確保。プロジェクトデータはバージョン付きJSON。録音音声は独立ファイル。
- iPhone Safariを対象に、初回タップでAudioContext開始／復帰、ページ非表示と再開、ポインターキャンセル、マルチタッチを検証。
- 性能面では描画の負荷制御（60fps目標、負荷時30fps）、Bug数制限、メモリの上限、AudioParam更新頻度の節約、master peakと非有限値の検査を行う。

## 8. 実装順序

| マイルストーン | 内容 | 完了条件 |
| --- | --- | --- |
| **M0 / Foundation** | 型定義、Canvas stage、Web Audio master、テスト環境 | 安全に音を鳴らし、再生・停止できる |
| **M1 / First Playable** | THUMP、CHIRP、TICK、1 Bug、明示的LINK、2つの初期シーン | タップ演奏、規則的な核、相互反応が一画面で成立 |
| **M2 / Transform** | MUTANT、移動／選択の改善、Bugの明示的なタップ介入 | 単体と組み合わせの音の違いが聴き取れる |
| **M3 / Memory** | MUMBLE、NEST、局所MUTATE、UNDO | 短い演奏を記憶し、変形し、戻せる |
| **M4 / Recording** | WAV書出、保存／呼出、iPhone Safari検証、軽量化 | 数分の演奏・録音と再読込が安定 |

初期版はM1を優先し、M2以降の未完成機能を無理に入れない。

## 9. 受け入れテスト

- 初回起動後、音声を開始するジェスチャーから30秒以内に**音を組み合わせて演奏できる**。
- チップ単体でも音が出る。TICKとのリンクにより、**一定のリズムと余白**ができる。音源との組み合わせにより音楽上意味のある違いが起こる。
- 4チップ + 1 Bug の画面で選択、移動、演奏、リンク、リンク解除がモバイル幅でも誤爆しにくい。
- 視覚イベントの同期は保つが、描画フレームドロップでaudio eventのタイミングが壊れない。
- ランダム生成はseedで再現可能。MUTATEは少なくとも1個の音楽上の特徴を保ち、UNDOで元へ戻る。
- Bugが勝手に発音やパラメーターを改変しない。明示的な操作だけが音へ介入する。
- 44.1/48kHzの自動PCM試験で非有限値なし／安定したpeak／過大ノード生成なし。実機測定は別途必要。
- 古いリポジトリの音源を移植する場合は、**耳で確認できる個性**を保つ。自動EQや無差別な音色補正を適用しない。

## 10. 成功の判定

**設計上のゴール:** 「何をしているかわからないほど複雑」ではなく、**何を操作したかは理解できるのに、組み合わせた音と小さな世界の反応にはまだ発見がある**こと。

「3つのチップだけでも5分触っていたいか」「音が面白くて録音したくなるか」「Bugの動きが発音と関係していると感じられるか」を実際の試奏で判断する。機能数、Bug数、画面の派手さは成功指標にしない。
